# 世界の進化を公開前に検証する

## 目的と現在地

Day 1を公開世界の基準として保ち、Day 5・Day 10などの姿を開発中に先取りして遊ぶ。面白さや整合性に問題があれば、その候補を作り直してから公開する。**検証用のDay 10は未来の試作品であり、本番の世界日を10へ進めたことを意味しない。**

2026-09-28時点の本番D1には公開済みのDay 1だけがあり、`world_settings.daily_advance` は `off`。現行のCronはこの設定が `on` になると日を自動で進め、創造案がなければ沈黙の日を公開する。公開判断の仕組みが整うまで、本番の自動進行は `off` のままにする。Day 1のゲーム仕様は [最初に作るゲームの仕様](FIRST_GAME_SPEC.md)、日ごとの体験は [体験の進化計画](EXPERIENCE_PLAN.md) を基準にする。

現在の確認用URL:

- [Day 1保存版](https://hakoniwa-day1.wagaya.workers.dev/) — Day 1以外を表示しない専用D1/R2。検証用の記録だけ作成できる。
- [進化テスト版](https://hakoniwa-evolution.wagaya.workers.dev/) — 本番と別の専用D1/R2。ここへ検証済みの世界データとコードを反映して遊ぶ。

進化テスト版は初期状態をDay 1にしてある。Day 5・Day 10の候補を試すときは、専用D1へDay 1から順に候補イベントを適用してからURLを開く。現時点では候補イベントの適用器とレビュー画面は未実装で、任意の数字へ直接飛ばす機能は置いていない。

## 三つの世界を混ぜない

| 場所 | 役割 | データと時計 | 書き込み |
| --- | --- | --- | --- |
| 本番 | 観測者が訪れる正史 | 公開済みの世界日、実際のアカウント・願い | 承認済みの公開操作だけ。開発実験には使わない |
| ローカル検証 | Day 1から任意の節目まで素早く試す | 専用のローカルD1/R2、固定した検証時刻、架空の観測者 | 何度でも作り直せる |
| 共有検証環境 | 開発者が候補のURLを共有して遊び、リリース前に確認する | 候補ごとに本番とは別のWorker・D1・R2・秘密値、検証時刻 | 検証用の操作だけ。Cronによる自動進行と本番Issue投稿を無効にする |

CloudflareのWorker環境を使う場合、D1/R2の結び先を環境ごとに明示し、検証環境が本番のリソースを参照しないことを設定とデプロイ前チェックで確かめる。**本番WorkerのVersion URLは分離した検証環境の代わりにならない。** そのURLは版を分けても既存の設定とリソースを使うため、未来の世界日を試す用途には使わない。[Cloudflareの環境](https://developers.cloudflare.com/workers/wrangler/environments/)、[D1の環境](https://developers.cloudflare.com/d1/configuration/environments/)、[Version URL](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/) を参照する。

共有検証環境は関係者だけが開けるようにする。テストでは架空の利用者と願いを使い、Google OAuthやGitHub Issueの本番連携を呼ばない。認証そのものの通し確認が必要なときだけ、検証専用の設定と送信先で別途行う。本番D1の全量コピーは個人情報・願いを含むため検証データにしない。

## Day 1を固定する

「固定」は本番DB全体を凍結する意味ではない。観測者のセーブや同意済みの願いは増えてよい。固定するのは**Day 1の公開風景と歴史**である。

1. 現在の公開Day 1から、個人情報を含まない基準セットを作る。対象は世界日、地形、存在、当たり判定、観察文、神託、創世日記、公開APIの応答、代表的な画面画像。コードのコミット、マイグレーション版、基準セットのハッシュも記録する。
2. 基準セットをGitで版管理し、変更には理由と差分のレビューを要する。見た目だけでなく、歩ける場所、五つの存在を調べた結果、願いの掲示板への到達も基準にする。
3. 以後のコード変更は、Day 1データを入れた検証環境でも動かす。未来の機能を追加しても、Day 1にまだ存在しない物や操作を見せない。
4. 本番のDay 1と基準セットを定期的に照合する。ただし日次画像の撮り直し時刻、個人セーブ、願いの件数など、変わり得る値は比較対象から外す。

基準画像の完全なピクセル一致だけを合格条件にしない。意図した描画改善はあり得るため、差分画像を見て承認する。一方、APIの世界内容と歩行・観察の結果が変わった場合は意図を明記する。

## 節目の世界を再現する

Day 5やDay 10をDBの数字だけ書き換えて表示しない。**Day 1の基準からDay 2、3…と候補の出来事を順に適用**し、その日までの能力と履歴が揃った状態を作る。

- 各世界日の検証シナリオに、開始状態、適用する創造イベント、必要な機能フラグ、固定時刻・天候、架空の観測者の行為を記す。創造の中身は試案であり、神が本番で何を創るかを先に確定しない。
- 同じコード版、シナリオ版、乱数種、検証時刻から同じ世界と結果を再現できるようにする。シナリオはDay 1からの適用順を含めて版管理する。
- 節目ごとに公開APIの応答、代表的なセーブ、画面画像、操作記録を成果物として残す。Day 1・5・10を並べ、何が増え、何が失われ、初見で気づけるかを確認する。
- 同じシナリオを使って別の設計案を比較できるよう、候補を枝分かれさせる。失敗案の検証DBは捨てて作り直せるが、判断の理由と観察結果は残す。

| 節目 | 実際に遊んで確かめること | 主な失敗の兆候 |
| --- | --- | --- |
| Day 1 | 歩く、五つの存在を調べる、日記を読む、ログインして再訪する、願いを書く | 初見で動けない、個人セーブが混ざる、既存の庭が壊れる |
| Day 5 | 拾う、持ち物を見る、調べながら拾う、持って再訪する | 拾う意味に気づけない、持ち替えが煩雑、同じ物を連打で増やせる |
| Day 10 | 置く、再訪して残りを見る、他の観測者の匿名の痕跡を見る、上限を試す | 痕跡が通路を塞ぐ、先着者が資源を独占する、他人の名前や位置が漏れる |
| 以後10日ごと | [体験の進化計画](EXPERIENCE_PLAN.md) のその段の「できること」と前段からのつながりを遊ぶ | 増えたものが使われない、過去の行為が壊れる、来られない日に不利益が出る |

節目だけでなく、間の日の公開候補も検証する。Day 5が良くてもDay 4の「拾う」導入が分かりにくければ、Day 5の合格にはしない。

共有検証環境には、ゲーム画面とは別に関係者用のレビュー画面を置く。Day 1・5・10の候補を選ぶと、その候補専用のWorkerとDBのURLでゲームを開ける。横には比較画像、前の節目から増えた行為、未解決の問題、判定結果を並べる。切替は検証環境の中だけで行い、公開APIや本番画面には任意の日を指定する入口を作らない。候補を再生成したらレビュー画面の版番号も変え、古い画面と取り違えない。

## 一回の検証サイクル

1. **仮説を書く。** その日の変化で観測者が何に気づき、何を試すはずかを一文で書く。仕様の受け入れ条件と、判断に使う操作を紐づける。
2. **候補を作る。** コードとシナリオを変更し、Day 1から目標日までローカルの使い捨て状態へ適用する。本番のデータと時計には触れない。
3. **機械で確かめる。** マイグレーション、API、歩行と当たり判定、セーブ、日付境界、二重操作、複数アカウント、通信断を検査する。Day 1の回帰も毎回実行する。
4. **人が遊ぶ。** まず説明なしで5〜10分遊び、次に意図した行為を試す。デスクトップとモバイルで画面を見て、Day 1・前の節目との比較画像と操作記録を残す。
5. **判定する。** `合格`、`要調整`、`設計変更` のいずれかと理由を記録する。要調整なら同じ節目を再生成して再検証し、設計変更なら [コンセプト](CONCEPT.md) と [Day 100のゲーム仕様](MIDDLE_GAME_SPEC.md) への影響を見直す。
6. **共有検証環境で通す。** 合格候補だけを隔離された環境へ置き、別端末・別アカウント、実際のWorker配信、D1/R2の結び先、公開用画面の構図を確認する。

判断の記録には、節目、コード版、シナリオ版、実行日時、確認者、画面、期待した行動、実際の行動、問題、変更した設計、再検証結果を残す。機能を作った事実だけで合格にしない。

## 公開ゲート

**Day Nを公開する条件:** Day Nまでのシナリオが順に再現できること、Day 1と前の公開日の回帰が通ること、その日の体験を人が確認したこと、共有検証環境でデータと秘密値の隔離を確認したこと、問題時に日を止める手順が実証されていること。判定結果を残し、合格前に本番の `daily_advance` を `on` にしない。

| 判定 | 扱い |
| --- | --- |
| 合格 | 候補のコード・シナリオ・検証結果を固定し、次の公開日の準備へ進む |
| 要調整 | 本番は前の公開日を維持する。同じ節目を修正・再生成し、操作と画面を再確認する |
| 設計変更 | 候補を正史に入れず、問題になった仮説と仕様を更新する。Day 1から新しい案を再実行し、後続の節目も再検証する |

公開はDay 5やDay 10へ飛ぶ操作ではない。合格済みのDay 2から順に、世界日を一日ずつ正史へ追加する。公開前には本番のバックアップを取り、コードとDBスキーマの互換性を確認する。公開後はAPI、日記、画面、保存、痕跡を確認する。問題が出た場合は進行を止める。既に公開された日を検証案のように消して作り直さず、次の日の訂正として残す。D1の時点復元は事故からの復旧に限る（[デプロイ手順](DEPLOYMENT.md)）。

現行の `daily_advance=on` は毎朝の自動進行であり、人が合格を押す公開ゲートにはなっていない。Day 2を実際に公開する前に、**検証済みの候補だけを原子的に公開し、未承認なら前日を見せ続ける手順**を実装・実証する必要がある。単に `on` にするだけでは、未完成の日を沈黙として進めてしまう。

## 最初に作る順序

1. Day 1の公開データと代表画像を、個人情報を除いた基準セットとして固定する。
2. ローカルD1を毎回Day 1から作れるようにし、任意の節目の検証シナリオを順に適用するコマンドを作る。
3. Day 1・5・10の操作と画像を再現し、差分を並べるレポートを作る。
4. 本番とは別のWorker・D1・R2を持つ共有検証環境を用意し、検証用の願いが本番Issueへ届かないことを確認する。
5. 公開ゲートと停止手順を実装し、Day 2の候補で一度通してから本番の世界日を動かす。

この文書は検証の設計であり、現時点で節目シナリオ、共有検証環境、公開ゲートが実装済みであるとは主張しない。
