# Day 100への進化 — 四つの軸

## 0. この文書の位置づけ

Day 100で何が成立していればよいかは [中期ゲーム仕様](MIDDLE_GAME_SPEC.md) を、公開順序と運営段階は [ロードマップ](ROADMAP.md) を正とする。

この文書が扱うのは、その間にある**差分の埋め方**である。現在のDay 1実装から中期仕様の状態へ至るために、システム、グラフィック、ゲーム性、ボリュームの四軸で何を作り替え、どこに判断点があり、どこで破綻するかを具体化する。

四軸は独立していない。システムのデータ化が済むまでグラフィックもゲーム性も日次では増やせず、ボリュームはその三つの上に乗る結果でしかない。依存関係は [7章](#7-四軸の依存関係と順序) に示す。

## 1. 現在地

| 項目 | Day 1（実装済み） | Day 100（到達点） |
| --- | --- | --- |
| 世界の定義 | `src/App.tsx` のTypeScript配列 | D1のデータ。コード変更なしで増える |
| 世界日 | `1` で固定 | 100日が進行し、全員が同じ日を見る |
| 地図 | 12×12タイル、歩行可能10×10の一画面 | 連続した5〜7地域をカメラが追う |
| 存在 | 5個（木、家、井戸、掲示板、池） | 60〜120個 |
| スプライト | CSSの図形。1個ずつ手書き | データから手続き的に生成 |
| 時間 | なし | 昼夜、天候、季節 |
| 動詞 | 移動、調べる | 移動、アクション（文脈で意味が変わる） |
| 観察文 | 存在ごとに固定文字列1つ | 状態、時刻、天候、履歴の関数 |
| 個人データ | `saves` に1つのJSON（16KBまで） | 観察、図鑑、庭、痕跡に分割 |
| D1テーブル | 6個 | 追記型イベントを中心に再編 |
| 日次処理 | 画面の撮影のみ | 創造サイクルの適用と撮影 |

現在のクライアントは静的な世界を描いている。地図も、オブジェクトの位置も、観察文も、すべてビルド成果物の中にある。**この状態のままでは、神が一日ひとつ創造しても、デプロイなしには世界へ現れない。** 四軸の中でこれが最初に壊すべき前提である。

## 2. システム的な進化

### 2.1 世界をコードからデータへ

最優先はこれ一つに尽きる。日次創造を担うAIは本番DB・Cloudflare・実行コードへ直接触れない（[世界の秘密](WORLD_SECRETS.md)、[システム構成](ARCHITECTURE.md)）。したがって創造の成果物は**データとして表現できるものに限られる**。逆にいえば、データで表現できない種類の創造は、Day 100までのAIには作れない。

- `world_entities`: 存在。誕生日、消滅日、種別、スプライト定義、観察テンプレートを持つ。
- `entity_tiles`: 存在が占めるタイル。当たり判定はここから導出し、見た目の大きさとは分離する（現在の実装でも、木の樹冠がタイルをはみ出しても衝突しないのと同じ原則）。
- `relationships`: 捕食、開花、受粉、発明などの因果グラフ。
- `world_tiles`: 地形、標高、生物群系。

クライアントは「現在の世界日の地図」をAPIから受け取って描く。`objects` 配列は初期データの投入元としてのみ残し、実行時の正にはしない。

### 2.2 世界日の進行と同一性

全観測者が同じ世界日を見ることは受け入れ条件である。

- `world_days` に公開済みの世界日と公開時刻を持ち、**公開は原子的に切り替える**。生成途中の状態を読ませない。
- 読み取りAPIは必ず世界日を固定して応答する。日付境界をまたぐ訪問で、同じ画面の中に2日分が混ざらないようにする。
- 日次処理が失敗した日は前日の安定版を配信し、沈黙として記録する。これは障害対応ではなく仕様上の選択肢として扱う。

### 2.3 追記型イベントとスナップショット

創造も自律変化も `creation_events` への追記とし、修正も新しいイベントにする。過去を上書きしないというプレイヤーへの約束が、そのままデータモデルの制約になる。

ただし追記型だけでは読み取りが破綻する。世界日100の地図を得るために100日分のイベントを毎回折り畳むのは遅い。

- 世界日ごとに materialized な `world_snapshots` を持つ。
- 公開済みの世界日の地図は**不変**であるため、エッジで長期キャッシュできる。キャッシュキーは世界日。
- 任意の世界日をステージングへ復元できることを、復元テストとして定期実行する。

### 2.4 セーブの構造化

現在のセーブは `{position, direction, worldDay}` を1つのJSONに入れた16KB上限のブロブである。Day 100では観察記録、図鑑、庭、痕跡が加わり、ブロブでは以下が成立しない。

- 図鑑の初観測を世界全体で集計する（誰が最初かは匿名でも、記録は共有世界側に要る）。
- 庭の成長をサーバー時刻で計算する。
- 一部だけを更新する（訪問のたびに全体を書き戻さない）。

`observations` / `player_gardens` / `traces` へ分割し、セーブにはスキーマ版番号を持たせる。**世界に存在する行為はDay 100まで増え続けるため、個人データの形も増える前提で設計する。**

### 2.5 創造サイクルの受け口

さくらVPSのcronからの署名付き `POST /admin/creation-cycle` を唯一の入口とする。

1. スキーマ検証（JSON、参照ID、規模上限、禁止操作）
2. ステージング世界での適用とシミュレーション
3. 人間の承認（低リスク変更のみ許可リストで自動化）
4. 本番への単一トランザクション適用
5. 失敗時のロールバックと、修復の新規イベント化

**即時停止手段を最初に作る。** 自動公開を許すのは、止める方法が実証された後に限る。

### 2.6 配信と費用

- 公開済み世界日の地図とスクリーンショットは不変なので、費用はキャッシュ効率でほぼ決まる。
- R2は1日1枚で100日でも十数MB規模にとどまる（現状73KB/枚）。費用の主因にならない。
- 主な変動費はAI生成側にある。1日1サイクル、入力は世界要約と関連する記憶に限定し、秘密の全文を毎日渡さない。

### 2.7 判断点

- **イベント折り畳みをどこまで許すか。** スナップショットなしで進めると、世界日30前後で地図取得が目に見えて遅くなる。
- **どの粒度でデータ化するか。** 地形まで完全にデータ化するか、地域の骨格は固定し内容物だけをデータにするか。後者の方が早く動くが、AIが地形を変えられなくなる。

## 3. グラフィックの進化

現在のスプライトはCSSの図形であり、1つずつ人が書いている。木、家、井戸、掲示板、池の5個でこの方式は成立しているが、**60〜120個の存在をAIが日次で増やす世界では成立しない。**

### 3.1 スプライトをデータにする

素朴な解は「AIに画像を生成させる」だが、これは二つの理由で採らない。

1. 100日分の生成画像は様式が揃わず、世界が一つに見えなくなる。
2. 任意の画像はモデレーション対象になり、公開前検査の難度が跳ね上がる。

採るのは**手続き的スプライト**である。AIは画像ではなく**パラメータ**を作る。

```text
{ kind: "plant", height: 3, trunk: "thin", canopy: "round",
  palette: "leaf_cool", sway: 0.4, seasons: { autumn: "leaf_warm" } }
```

クライアント（またはビルド時のジェネレータ）が、このパラメータから既定の様式で描画する。新種が生まれてもコードを変えずに描け、パレットと形状の語彙が固定されているため様式が崩れない。表現力は落ちるが、**日次創造が視覚を伴うための唯一の現実的な方法**である。

手続きで表現しきれない中心的な存在（固有NPC、地域の象徴物）は、人が作った少数のアセットとして例外的に持つ。

### 3.2 タイルの層と高さ

現在は地面タイル1層に、深度ソートしたオブジェクトを重ねているだけである。Day 100では最低限これだけの層が要る。

- 地形層（草、土、水、砂、石などの生物群系）
- 標高層（崖、水深、段差）
- 装飾層（花、足跡、水やりの跡などの痕跡）
- 存在層（深度ソート済み）
- 光・天候層（画面全体への色調と粒子）

標高は等角投影では単純で、1段につき画面上へ `th/2` ずらし、深度ソートのキーに高さを加えるだけでよい。ただし**当たり判定と段差の昇降規則を同時に決めないと、見た目だけ立体で歩けない地形が増える。**

### 3.3 時間・天候・光

投資対効果が最も高いのはここである。既存のタイルと存在をひとつも増やさずに、同じ場所が朝と夕で違って見える。観察文が時刻と天候の関数になる（[中期ゲーム仕様 6章](MIDDLE_GAME_SPEC.md)）ための視覚的な裏付けでもある。

- 昼夜は画面全体への色調変換として実装する。個々のスプライトに夜用の絵を持たせない。
- 天候は層として重ね、存在ごとの対応を必須にしない。
- 動きを減らすOS設定では、粒子と揺れを止め、色調だけを残す。

### 3.4 カメラと描画方式の切り替え点

現在は地図全体が一画面に収まり、カメラが存在しない。地域が増えればカメラが要る。

- タイル数が増えるため、可視範囲＋余白だけを描画する（カリング）。
- 現在のDOM描画は155ノード程度。**目安として1,500ノードを超えたあたりから初回描画とスクロールが怪しくなる。** 数千タイルと天候粒子が同時に必要になった時点でcanvasへ移す。
- 先回りしてcanvasにはしない。DOMのままの方が、アクセシビリティ（ラベル、フォーカス）とCSSによる様式の調整が容易であり、現時点の規模では有利である。

判断は規模で決める。**先行指標は初回描画時間とスクロール中のフレーム落ちであり、これを計測してから切り替える。**

### 3.5 アニメーション

現在はプレイヤーの移動に90msのトランジションがあるだけである。追加するのは、待機と歩行、植物の揺れ、水面、天候まで。いずれも手続きスプライトのパラメータから駆動し、存在ごとに個別実装しない。

### 3.6 日次スクリーンショットの構図

現在は地図全体が一画面に収まるため、`?capture=1` でHUDを隠して撮ればそれが世界の全景になる。カメラが導入されると**何を撮るかを決めなければならない。**

- その日の中心となる創造が起きた場所を撮る（日記と画像が一致する）
- 村の定点を撮る（100日並べたとき変化が読める）

両方を撮って日記側で選べるようにするのが素直である。定点は歴史の比較に、創造地点はその日の記録に効く。

### 3.7 様式の不変条件

100日間ぶん、別々の日に作られたものが一つの世界に見えるための契約。現在の実装で既に守っている規則を明文化し、手続きスプライトのジェネレータにも強制する。

- 等角投影は2:1。斜辺の傾きは常に `1/2`。
- 光源は右上。左面が暗く、右面が明るい。
- 接地は影の楕円で示し、タイル中心に置く。
- 1×1または2×2など、フットプリントはタイルの整数倍。
- 色はパレットから選ぶ。任意の色値を許さない。

## 4. ゲーム性の進化

### 4.1 動詞を増やさない

Day 1の「移動して、近づいて、アクションする」を最後まで核にする。植える、汲む、話す、拾うは新しいボタンではなく、**位置と対象によって意味が変わる同じアクション**として表現する。

これは操作の簡潔さのためだけではない。動詞が固定されていれば、AIが新しい存在を作るときに定義すべきは「この対象にアクションしたとき何が起きるか」だけになり、創造がデータに収まる。**動詞を増やす設計は、そのままシステム側の破綻につながる。**

### 4.2 観察を状態の関数にする

現在の `act()` は存在ごとに固定の文字列を返す。これはDay 1では成立するが、同じ文章を100日読ませることはできない。

観察結果を、初回か再訪か、世界日と季節、時刻と天候、成長段階、周囲の存在、過去の自分の行為、の関数にする。**実装としては分岐のコードではなく、状態セレクタつきのテンプレート群をデータで持つ。**

### 4.3 発見と図鑑

発見は既知の対象を調べ直すことでは成立しない。条件が満たされた状態での観測を記録する。

- 検証可能な条件（雨の日だけ咲く、特定の実を食べる、二種が隣接したときだけ起こる）を、判定可能なデータとして持つ。
- 総数、完成率、未発見のシルエットを出さない。空白があることを見せない。
- 消滅した存在も履歴として残す。

### 4.4 庭

観測者ごとの実験場所であり、倉庫でも効率農場でもない。サーバー時刻で成長を計算し、長期離脱でも全滅させない。庭で起きた現象は匿名かつ集約して、共有世界の次の創造の入力になり得る。

### 4.5 NPC

少人数で始め、それぞれに居場所、日課、記憶を持たせる。依頼配布装置にしない。

Day 100付近でNPCが果たすべき役割が一つある。**同じ出来事を複数のNPCが異なる解釈で語ること。** 世界に唯一の正解がないことの表現であり、神託の語彙が二系統に見え始める長期伏線（[世界の秘密](WORLD_SECRETS.md)）の受け皿でもある。

### 4.6 村の外とバトル

村の外のフィールド、回避可能な敵、簡潔な成長、クラフトは中期仕様にある。ただしこれは**最後に入れる**。理由は単純で、この軸だけが「観測者であって主人公ではない」という核を壊しやすいためである。

- 戦闘は探索の季節性と危険度を表すために置き、主ループにしない。
- 敵にも生態と居場所を与え、倒す以外の解決を用意する。
- 恒久的な取り返しのつかない損失を作らない。

**先行指標を決めておく。1回の訪問に占める戦闘時間の比率が観察と探索を上回ったら、設計が反転した合図として扱う。**

### 4.7 願いと因果の可視化

Day 100での感情的な到達点はここにある。`wish_links` によって、自分が昔送った願いが、直接ではない形で現在の世界へ結びついていることを見られる状態にする。採用率や順位は見せない。叶わなかった願いにも失敗判定を付けない。

## 5. ボリュームの進化

### 5.1 到達点の目安

確定値ではなく規模感の目安とする。徒歩で関係を理解できる小ささを保つことが上限を決める。

| 対象 | Day 1 | Day 100の目安 |
| --- | --- | --- |
| 世界日 | 1 | 100（神託または沈黙の記録つき） |
| 地域 | 1 | 5〜7（連続した地形） |
| 描画タイル | 144 | 3,000〜6,000 |
| 存在 | 5 | 60〜120 |
| NPC | 0 | 5〜8 |
| 図鑑項目 | 0 | 80〜150 |
| 行為・レシピ | 1（調べる） | 20〜40 |
| 観察文 | 5 | テンプレート数百、組み合わせは桁違い |

### 5.2 ボリュームは前倒しで作らない

100日分を先に作ろうとすれば破綻する。**1日に1つの中心概念という制約は、演出上の方針であると同時に、生産速度の設計でもある。**

- 1日の創造で増えるのは、存在1つとその観察テンプレート、関係、日記1件。
- これを100回繰り返した結果が、Day 100のボリュームになる。
- 作り置きしないため、世界の因果が常に直近の状態と噛み合う。

### 5.3 観察文の組み合わせ爆発を避ける

1つの存在に対し、初回／再訪 × 季節4 × 天候3 × 時刻3 × 成長段階3 を全て書けば1存在あたり200文を超え、100存在で数万文になる。到達不能である。

- 文はテンプレートと状態スロットで持ち、全組み合わせを書かない。
- 差分を出すのは**その存在にとって意味のある軸だけ**にする（花なら天候と季節、井戸なら時刻、NPCなら記憶）。
- 差分がない軸では、文章を変えずに見た目と音を変える。

### 5.4 読む側のボリューム

100日ぶんの歴史は、書く問題であると同時に**読む問題**である。復帰者が100件の日記を順に読むことを前提にしない。

- 最終訪問日から今日までを一覧できる。
- 唯一の要約を強制しない。
- 地域、存在、願いといった関心から横断して辿れる。
- 「この変化はどこから来たか」を関連項目でさかのぼれる。

### 5.5 運営コスト

- スクリーンショット: 100枚で十数MB。問題にならない。
- D1: 創造イベントは数千行規模。スナップショットの方が容量を使う。
- AI: 1日1サイクル。コストは入力コンテキストの長さで決まるため、世界要約と関連記憶に絞る。

## 6. 破綻点と先行指標

軸ごとに、何が起きたら設計が破綻しているかと、それに先に気づくための指標を決めておく。

| 軸 | 破綻の条件 | 先行指標 | 対処 |
| --- | --- | --- | --- |
| システム | 創造のたびにデプロイが必要 | 1創造あたりのデプロイ回数が0でない | 世界のデータ化を優先 |
| システム | 世界日の取得が遅い | 地図取得APIのp95 | 世界日ごとのスナップショット |
| グラフィック | 様式が崩れ一つの世界に見えない | 新規スプライトのパレット逸脱 | 手続き生成とパレット固定 |
| グラフィック | 描画が重い | 初回描画時間、スクロールのフレーム落ち | カリング、必要ならcanvasへ |
| ゲーム性 | 同じ観察文で飽きる | 再観察の割合 | 観察を状態の関数にする |
| ゲーム性 | 戦闘が主ループを乗っ取る | 訪問あたりの戦闘時間比 | 回避可能性と報酬設計の見直し |
| ボリューム | 文章量が作れない | 1存在あたりの必要文数 | テンプレートと意味のある軸への限定 |
| ボリューム | 100日を読めない | 復帰者の日記離脱 | 関心軸での横断閲覧 |

## 7. 四軸の依存関係と順序

前の段が済まないうちに次へ進むと、後で作り直しになる箇所を示す。ロードマップのPhaseと対応させて読む。

1. **世界のデータ化と世界日の進行**（システム）— 他のすべての前提。ここが終わるまで日次創造は成立しない。
2. **追記型イベントとスナップショット**（システム）— 過去を消さない約束と、読み取り性能の両立。
3. **時間・天候・光**（グラフィック）— 新規コンテンツなしで既存の価値を増やす最小投資。観察の関数化の前提でもある。
4. **観察の関数化と図鑑**（ゲーム性）— 3が済んでいれば、差分の軸が既に世界側に存在している。
5. **手続きスプライト**（グラフィック）— 日次創造が視覚を伴うための前提。ここから存在数を増やせる。
